> **版本约定**：开发文档版本号与项目版本号对齐，文件名为 `开发文档_v{x.y.z}.md`。
> 历史版本：[v0.6.0](开发文档_v0.6.0.md) · [v0.6.1](开发文档_v0.6.1.md) · [v0.6.2](开发文档_v0.6.2.md)。
> 沟通时间线见 [开发日志.md](开发日志.md)，变更摘要见 [CHANGELOG.md](CHANGELOG.md)。

**v0.7.0 状态**：整体加固版。本版不新增产出品类，而是对已完成的全部代码做了一轮"第一性原理 + 对抗性审查"，把审查出的 17 项问题全部修复，覆盖四个维度：**稳定性**（数据损坏防护、重启僵尸任务、SSE 线程占用）、**质量**（修订截断、截断检测、GBK 编码、短课堂纲目）、**速度**（流式进度、存在性检查、超时与连接复用）、**安全**（路径穿越、API Key 脱敏、渲染消毒）。

---

## 1. 版本定位

v0.6.x 完成了功能闭环：上传素材 → 分步生成五产出 → 持续修订 → 版本历史 → 导出。日常使用没有明显缺功能，但一轮对抗性审查（假设每一步都在最坏时刻失败）暴露出一批真实风险：

- 修订长产出必被静默截断（输出上限写死 4096）。
- 全链路不看 `finish_reason`，模型被掐断时用户拿到"看起来完整"的残缺纪要。
- `providers.json` 非原子写，损坏后会被静默重置，用户配置全丢。
- 上传文件名不校验，构造 `../../` 可写到会话目录之外。
- 服务重启后进行中的任务变成前端永远"生成中…"的僵尸。
- GBK 编码的转写稿（讯飞/WPS 常见）被按 UTF-8 强读，静默变成乱码。
- 30 分钟的短课堂被硬性下限摊成 20 个阶段。

v0.7.0 把这批问题一次修完，并顺手兑现了 v0.6.2"已知取舍"里挂账的三项：DOMPurify、截断原因识别、生成中间进度。

## 2. 修复清单（按维度）

### 2.1 稳定性

| 编号 | 问题 | 修复 |
|------|------|------|
| S5 | `providers.json` 直写非原子，损坏后被静默重置播种，用户配置全丢 | 原子写（tmp + rename）；解析失败时把坏文件改名 `providers.json.corrupt-<ts>` 保留现场再播种 |
| S6 | `meta.json` 多一个未知字段就抛 TypeError，一个坏会话拖垮整个会话列表 | 按 dataclass 字段过滤未知键；任何异常返回 None，列表自然跳过 |
| S7 | 服务重启后进行中的任务无终态事件，前端永远"生成中…" + SSE 无限重连 | 启动时（lifespan）扫描所有 `progress/<step>.json`，末事件非 done/error 的补写一条中断 error |
| S8 | 每条 SSE 订阅独占一个线程池线程（anyio 默认 40），多 Tab 并发可拖死全部 API | SSE 改 async 生成器 + 非阻塞轮询队列，不再占用线程池线程 |
| S9 | Provider 每次调用新建 SDK client、无超时（默认 10 分钟），中转站挂起时 worker 被吊死 | client 按 provider 实例惰性缓存复用；显式 `timeout=180s` |
| S14b | 进度文件每事件全量直写，可能被读到半截 | 原子写；瞬态流式事件只推订阅者、不落盘 |

## 3. 关键机制说明

### 3.1 截断防护链

```text
供应商配置 max_output_tokens（0=不限）
  → chat() 请求前收敛 max_tokens
  → SDK 返回 finish_reason 规范化为 stop/length
  → engine._call 遇 length 抛 ProviderError（不落盘残缺产出）
  → 例外：实录纠错块截断按失败处理，走重试→确定性清洗兜底
```

用户视角：以前"纪要看起来完整其实尾部缺失"，现在要么完整、要么明确报错提示换更大输出上限的模型。

### 3.2 流式进度

`chat(..., on_delta=...)` 时走 SDK 流式接口；engine 用 `_streamed_call`（线程 + 队列的生成器）把增量折算成瞬态事件：

```text
data: {"type":"step","percent":16,"message":"已生成约 137 字…","transient":true}
```

- 节流：每 2 秒最多一条；percent 封顶 93，终态仍由 done/error 决定。
- 瞬态事件不落盘（不撑爆 progress.json），刷新后回放看不到中间字数属预期。
- 中转站不支持 stream：首个增量前失败自动降级为非流式，结果不受影响。
- 应用范围：撷要、笺注、修订、纲目汇编/修复；实录分块与脉络保持原状（前者已有块级进度，后者输出很短）。

### 3.3 重启自愈

启动时 `mark_interrupted_runs()` 扫描全部会话的进度文件，为没有终态的任务补写：

```json
{"type": "error", "message": "任务因服务重启而中断，请重新生成。"}
```

前端首屏恢复与 SSE 回放都会拿到这条终态，僵尸"生成中"消失。配合前端 onerror 兜底，服务不可达场景也能在约 15 秒内明确报错。

### 3.4 API Key 生命周期

```text
录入：表单敲入 → POST/PUT 明文提交（本地服务）→ providers.json 落盘
回显：GET 详情只给 api_key_masked（前4…后4）+ has_key，明文恒为 ""
编辑：key 框留空 → PUT 不带 api_key 字段 → 后端 patch 语义保留原 key
测试：草稿 key 为空且带 provider id → 后端借用已存 key 测试
```

注：providers.json 本身仍是明文存储（本地单用户定位），上云前需再加一层。

## 4. API 变更

只增不删，一处字段语义变更：

| 接口 | 变更 |
|------|------|
| `GET /api/providers/{pid}` | **`api_key` 恒为空**（原为明文）；新增 `api_key_masked`、`has_key`、`max_output_tokens` |
| `GET /api/providers` | 每项新增 `max_output_tokens` |
| `POST/PUT /api/providers*` | 接受 `max_output_tokens`；PUT 不带 `api_key` 字段时保留原 key |
| `POST /api/providers/test` | `provider` + `config` 可同给：草稿 key 为空时借用已存 key |
| `GET /api/sessions/{sid}` | 新增 `resolved_step_models`（每步最终生效的 provider/model/source；仅详情接口，列表不带） |
| `POST /api/sessions/{sid}/run-step` 等 | step 参数白名单校验，非法返回 400 |
| `POST /api/sessions/{sid}/inputs` | 文件名净化为 basename；空/`.`/`..` 返回 400 |
| SSE 事件 | 可能出现 `transient: true` 的 step 事件（流式进度），前端按普通 step 事件处理即可 |

### 5.2 真实冒烟（隔离 DATA_DIR 起服务）

- 上传 `filename=../../meta.json` → 净化为 `meta.json` 落在 inputs/ 内；纯 `..` → 400。
- 上传 GB18030 编码转写稿 → 实录生成内容正确（真实调用 DeepSeek 全链路）。
- `step=../../evil` / `step=zzz` → 400。
- Provider 详情 → `api_key:""` + 掩码 + has_key。
- 撷要生成 → SSE 可见 `已生成约 N 字…` 瞬态事件，落盘 progress.json 不含瞬态事件。
- 伪造未完成进度文件 + 重启服务 → 自动补写中断 error，`/progress` 正确反映。

## 6. 已知取舍

1. **providers.json 明文存 key**：本地单用户定位下接受；上云前必须改（系统钥匙串或加密）。
2. **流式进度的 percent 是启发式**（字数折算、封顶 93），不代表真实完成比例；终态以 done/error 为准。
3. **PDF 仍未接入**：本版从上传 accept 中移除，避免"能传但被静默忽略"的误导；等真实样例后按辅助素材接入。
4. **所有 txt/md 仍一律当转写稿拼接**：输入角色区分（主稿/辅助文本）需要交互设计配合，留待下版。
5. **Mermaid chunk 体积**（构建告警 800KB+）：既有问题，后续按需加载。
